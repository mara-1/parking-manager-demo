# Порядок работы с исходным кодом

## Коммиты — Conventional Commits

Формат заголовка: `<тип>(<область>): <описание>`

| Тип | Назначение |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление ошибки |
| `refactor` | изменение кода без изменения поведения |
| `test` | тесты |
| `docs` | документация |
| `style` | форматирование, без изменения логики |
| `perf` | оптимизация производительности |
| `build` | сборка, зависимости проекта |
| `ci` | пайплайны GitHub Actions |
| `chore` | прочие служебные изменения |
| `revert` | отмена ранее сделанного коммита |

Области: `auth`, `parking`, `billing`, `booking`, `reports`, `ui`, `data`, `repo`, `ci`, `deps`.

Правила: описание — с маленькой буквы, в повелительном наклонении, без точки в конце;
заголовок не длиннее 100 символов; один коммит — одно логическое изменение;
несовместимое изменение помечается `!` после типа или области.

```
feat(parking): добавить регистрацию въезда автомобиля
fix(billing): исправить округление стоимости до рубля
test(booking): добавить тесты пересечения бронирований
```

Проверка выполняется локально хуком `.githooks/commit-msg`
(подключение: `git config core.hooksPath .githooks`) и в CI (`commitlint`).

## Ветвление — Git Flow

| Ветка | Создаётся от | Вливается в | Назначение |
|---|---|---|---|
| `main` | — | — | стабильные релизные версии, каждая помечена тегом |
| `develop` | `main` | — | интеграция готовых функций |
| `feature/<№ задачи>-<кратко>` | `develop` | `develop` | разработка одной задачи из Trello |
| `release-<версия>` | `develop` | `main` и `develop` | подготовка релиза в конце этапа |
| `hotfix-<версия>` | `main` | `main` и `develop` | срочное исправление релиза |

Пример: `feature/05-auth`, `release-0.1.0`, `hotfix-0.1.1`.

## Слияние

- Прямые push в `main` и `develop` запрещены — только через pull request.
- Слияние возможно только после успешных проверок `lint`, `test`, `build`, `commitlint`.
- Способ слияния — merge commit (`--no-ff`), squash и rebase отключены.
- После слияния ветка `feature/*` удаляется.

## Релиз

Версии по Semantic Versioning (`MAJOR.MINOR.PATCH`), релиз — в конце каждого этапа.

1. `git checkout -b release-0.2.0 develop` — стабилизация, исправления.
2. Pull request `release-0.2.0` → `main`, слияние после проверок.
3. `git tag -a v0.2.0 -m "Этап 3. Реализация I"` на `main`, `git push origin v0.2.0`.
4. Workflow `Release` замеряет метрики, собирает приложение и публикует GitHub Release.
5. Pull request `main` → `develop`, чтобы исправления из релизной ветки попали в разработку.
